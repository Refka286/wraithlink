00Origine de la demande

Deux temps distincts : d'abord amplifier un document de planification, ensuite le construire réellement.

La session a commencé par une demande d'amplification du fichier Plan_de_Travail_Wraithlink.md, un plan de travail de PFE déjà structuré en 7 sections. Cette première passe a ajouté une formule de scoring de risque détaillée, un modèle de données PostgreSQL, une spécification API REST, un schéma JSON pour les adaptateurs d'outils, un diagramme de machine à états, une section sécurité de la plateforme elle-même, un planning détaillé par sprint et un registre de risques projet — faisant passer le document de 127 à environ 500 lignes.

Une tentative de transmettre ce plan à un outil de raffinement distant (Ultraplan) a échoué faute de dépôt Git initialisé — l'occasion de créer le premier commit du projet. Ensuite est venue la demande explicite : construire réellement la plateforme, phase par phase, sans s'arrêter, avec trois contraintes fermes — aucun emoji nulle part, du code sans ton IA, et une palette strictement rouge / bleu / noir pour le frontend.

03Moteur de risque, machine à états, audit

Le cœur du positionnement d'Wraithlink : transformer une formule de risque en décision automatique traçable.

Phase 3 — Moteur de risque et porte d'approbation

terminé

Formule Score = Impact × Détectabilité / Réversibilité, testée contre les six exemples chiffrés du plan de travail. Une règle dure force le tier Interdit dès que la réversibilité vaut 1, indépendamment du score — c'est ce qui bloque DCSync même si son score numérique reste inférieur au seuil.

Le journal d'audit chaîne chaque entrée par hash SHA-256 sur l'entrée précédente : modifier une ligne passée casse la chaîne, ce qui est vérifié par un test dédié qui altère volontairement une entrée et confirme que la vérification échoue.

04API REST, authentification, orchestration Celery

FastAPI, JWT, RBAC pentester/reader, et l'exécution asynchrone des adaptateurs.

Phase 2 — Endpoints, workers, câblage

terminé

Les routers /engagements, /actions, /approvals, /findings, /reports et /auth sont posés sur le moteur de risque : une action automatique part immédiatement en tâche Celery, une action approbation met l'engagement en pause à approval_pending, une action interdite est enregistrée comme bloquée sans jamais toucher au statut de l'engagement.

Authentification par bcrypt direct (passlib s'est révélé incompatible avec bcrypt 5.x, voir bugs), pas d'endpoint d'inscription publique — les comptes se créent uniquement via un script shell côté serveur.

05Génération de rapport PDF

Un template Jinja2 rendu en PDF par WeasyPrint, alimenté par les données réelles d'un engagement.

Phase 6 — Moteur de reporting

terminé, vérifié avec un vrai PDF

Le rapport rassemble les cibles, les vulnérabilités, les actions exécutées et le journal d'audit complet d'un engagement. La palette rouge/bleu/noir du frontend est reprise dans le PDF pour la cohérence visuelle du livrable client.

07Frontend React

Dashboard, porte d'approbation, palette stricte — sans une seule autre couleur d'accent que le rouge et le bleu.

React + TypeScript + Tailwind, avec une configuration Tailwind qui remplace entièrement la palette par défaut : seules trois familles existent — red, blue, ink (noir/gris neutre). Aucune couleur verte, jaune ou violette n'est disponible dans le système de design, donc aucune ne peut apparaître par erreur.

La page centrale, EngagementDetail, affiche le fil des actions en direct (rafraîchi toutes les quatre secondes), et fait apparaître la ApprovalPanel — la porte d'approbation avec ses deux options A/B et sa justification obligatoire — dès qu'une action passe en attente.

08Vérification Docker réelle

La partie la plus longue de la session : prouver que la plateforme fonctionne vraiment, pas seulement que ses tests unitaires passent.

Après les cinq premiers commits (Phases 0 à 6), la totalité de la stack a été montée via docker compose up et exercée de bout en bout : connexion, création d'un engagement avec validation de portée obligatoire, soumission d'une action automatique (nmap, exécuté réellement dans le conteneur Linux), soumission d'une action d'approbation (sqlmap), décision d'approbation avec justification, blocage d'une action interdite (DCSync) sans effet sur le statut de l'engagement, et génération d'un rapport PDF réel.

09Bugs réels trouvés et corrigés

Chacun de ces bugs n'est apparu qu'en testant contre la vraie stack — aucun n'aurait été détecté en relisant le code seul.

Crash worker

Action sans cible faisait planter Celery et restait bloquée pour toujours

Scénario : soumettre une action sans target_id ni params.target provoquait un TypeError non capturé au fond de subprocess.run(None, ...), laissant l'action bloquée en statut running indéfiniment, sans trace d'erreur.

Correction : validation à la création (rejet HTTP 400 si aucune cible n'est fournie), et un filet de sécurité dans execute_action qui garantit qu'aucune action ne peut plus rester bloquée dans un état non terminal, quelle que soit l'exception levée par un adaptateur.

Dépendance

Génération PDF cassée par une dépendance transitive non épinglée

Scénario : weasyprint==62.3 était épinglé, mais pas pydyf (sa dépendance de génération PDF). pip a résolu pydyf 0.12.1, incompatible avec l'API attendue par weasyprint 62.3 — AttributeError: 'super' object has no attribute 'transform' sur chaque appel.

Correction : mise à jour vers weasyprint==69.0, vérifiée en générant et inspectant un vrai PDF (en-tête %PDF-1.7, contenu exact) depuis un engagement réel.

Image Docker

Nom de paquet Debian obsolète

libgdk-pixbuf2.0-0, utilisé par le Dockerfile backend, n'existe plus sur Debian trixie (base actuelle de python:3.11-slim) — renommé en libgdk-pixbuf-2.0-0.

Machine à états

Transition manquante : reconnaissance → approval_pending

Une action de tier approbation soumise directement depuis le statut reconnaissance (sans action automatique préalable) n'avait aucune transition valide vers approval_pending — l'engagement ne pouvait donc jamais se mettre en pause dans ce cas précis. Arête ajoutée à la machine à états.

Parsing

Extraction de compte Kerberoastable retournait une chaîne vide

'*svc_sql'.split('*')[0] retourne '', pas 'svc_sql' — l'adaptateur NetExec récupérait donc un nom de compte vide sur chaque hash Kerberoast parsé. Corrigé en .lstrip('*'), prouvé par un test qui aurait échoué avec l'ancien code.

Audit

Le chemin « outil inconnu » sautait la journalisation d'audit

Découvert en écrivant le test de non-régression lui-même : soumettre une action pour un outil non enregistré marquait l'action en échec mais retournait avant d'appeler append_entry — la seule sortie d'execute_action qui ne laissait aucune trace dans le journal d'audit.

Bcrypt

passlib incompatible avec bcrypt 5.x

La routine d'auto-détection interne de passlib 1.7.4 plante sur bcrypt≥4.1 (password cannot be longer than 72 bytes, un faux positif de sa détection de bug). Remplacé par des appels directs à la librairie bcrypt, contournant entièrement le bug.

10Installation des outils dans le conteneur worker

Chaque outil offensif doit réellement être présent dans le conteneur qui exécute les adaptateurs — sinon l'adaptateur le signale honnêtement plutôt que de simuler un résultat. Cette section a été le fil le plus long de l'après-rapport initial : l'utilisateur testait la plateforme en direct, action par action, et chaque outil manquant est apparu un par un.

Le découverte : backend et worker sont deux conteneurs distincts

Premier réflexe en voyant l'erreur required binary 'sqlmap' is not installed : installer sqlmap dans le conteneur backend. Erreur — l'API et le worker Celery partagent la même image Docker mais tournent dans deux conteneurs séparés, et c'est le worker qui exécute réellement les adaptateurs via subprocess. L'installation dans backend n'avait donc aucun effet ; il a fallu la refaire dans worker.

$ docker compose exec -u root worker sh -c "apt-get update -qq && apt-get install -y sqlmap" Setting up sqlmap (1.9.6-1) ... $ docker compose exec -u root worker sh -c "apt-get install -y ffuf" Setting up ffuf (2.1.0-1+b9) ...

nuclei : la limite réelle de cette connexion

nuclei n'est pas empaqueté pour Debian (outil Go, distribué via go install). Une première tentative a installé golang-go par apt en direct dans le worker — abandonnée en cours de route car trop lente et redondante avec une approche plus propre déjà décidée : un build Docker multi-étage, avec une étape FROM golang:1.23-bookworm qui compile nuclei séparément, dont seul le binaire final est copié dans l'image de production Python. Cette approche évite de laisser toute la chaîne de compilation Go dans l'image finale.

Le premier build complet a échoué avec short read: expected 64400050 bytes but got 53128318: unexpected EOF — une coupure réseau en plein téléchargement de l'image golang:1.23-bookworm. Une deuxième tentative a été relancée ; au moment de la rédaction de cette mise à jour, elle est toujours en cours, avançant lentement (plusieurs centaines de secondes pour quelques dizaines de mégaoctets) mais sans être bloquée — juste au rythme de cette connexion.

Build annulé

Un build en cours devient obsolète dès que le Dockerfile change

Après avoir lancé un premier rebuild pour sqlmap/ffuf, le Dockerfile a été modifié à nouveau (ajout de l'étape multi-stage nuclei) pendant que ce premier build tournait encore. Docker Buildkit lit le Dockerfile au moment du lancement, pas en continu — le build en cours restait donc basé sur l'ancienne version, sans nuclei. Plutôt que d'attendre inutilement sa fin puis relancer un second build complet, il a été interrompu et un unique build propre relancé avec le Dockerfile à jour.

Limite connue

Image Docker du frontend jamais construite avec succès

L'installation npm ci dans le Dockerfile du frontend a échoué deux fois pour des raisons purement réseau (ECONNRESET après 70 secondes de téléchargement, malgré une configuration de retry npm ajoutée). Le frontend reste entièrement vérifié — build TypeScript propre, npm run dev fonctionnel, CORS testé en direct contre le backend conteneurisé — mais tourne actuellement via le serveur de développement Vite plutôt que dans son propre conteneur.

En cours

Build nuclei toujours en vol

Au moment de cette mise à jour, le build multi-étage de nuclei tourne toujours en arrière-plan, ralenti par la même connexion instable. nmap, sqlmap et ffuf sont d'ores et déjà actifs dans le conteneur worker en cours d'exécution et utilisables immédiatement — seul nuclei reste indisponible en attendant la fin de ce build.

49 tests automatisés côté backend passent sur une base de données propre, couvrant le moteur de risque, la machine à états, le chaînage du journal d'audit, les parseurs de chaque adaptateur, et le flux API complet incluant le contrôle d'accès par rôle.
